# Database Schema Specification

## Conventions

PostgreSQL/Supabase types are shown. All primary IDs are server-generated `uuid`. Tables have `created_at timestamptz not null default now()` and `updated_at timestamptz not null default now()` unless stated otherwise; a database trigger maintains `updated_at`. Application deletion is normally archival/deactivation, not hard deletion. `profiles.id` equals the Supabase Auth user ID and is the only identity RLS trusts.

## Cross-table integrity

Foreign keys alone cannot prove all school relationships. A security-definer database function or server-side transaction must verify that teacher assignment, class, student, parent link, and update share one school before inserting/updating `student_updates`, acknowledgements, attendance, or announcements. Browser-supplied `school_id`, `teacher_id`, and `parent_id` are ignored/rejected when inconsistent with `auth.uid()`.

## Derived principal coverage

Do not store a fake aggregate. A restricted SQL view/function derives, per principal’s school and time period: sent updates, distinct updates with at least one acknowledgement, awaiting acknowledgement (active linked parent exists but no acknowledgement), and classes with no sent updates in the chosen period.
